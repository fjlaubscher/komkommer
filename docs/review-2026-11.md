# Komkommer review, November 2026

Review only. This file is the whole change. No engine source is modified here, and this pull request should stay a draft until the notes on it are settled.

Reviewed against `main` at `10e5c8a` (14 November 2026).

## Summary

The day-to-day build is already Ninja, and the language is already C++11. The engines are still Westwood's memory layout, and that layout is the multiplayer and save contract. The useful work is small, and it has a strict order: make every pull request compile and run the tests that exist, lock the save and packet layouts so a later cleanup cannot silently corrupt them, then move the project to C++17, and only after that share one more duplicated walk at a time.

Pull requests **#9, #10, #11, and #12 are merged**, not open. They are the pattern this plan continues. The only other open pull request today is **#22** (draft diagnostics for the mission-start music cut-off, issue #21). Leave that branch alone. This plan does not touch audio streaming.

Five recommendations, in order:

1. Run a compile of both games, a 32-bit Remastered DLL compile, and CTest on every push and pull request. Keep the existing `v*` workflows as the release publishers.
2. Adopt **C++17** as the project standard. GCC 11 on `ubuntu-22.04`, Apple Clang on `macos-15`, and Visual Studio 2022 (x86 and x64) all implement it. Leave C++20 until the Linux runner is past GCC 11.
3. Keep **Ninja Multi-Config**. Delete the two Visual Studio 2019 presets. Take 32-bit versus 64-bit from the Native Tools prompt, and make CMake refuse a Remastered configure that is not 32-bit.
4. Add compile-time checks for save offsets and for the numeric ids of `RALLY` / `CANCEL_QUEUE`. A `sizeof` sum misses a swap of two fields that happen to be the same size.
5. Share the next duplicated walks in this order: the A* search, the rally-flag update, the production-queue steps. Each one follows `common/selectscan.h`: a small header, a callback for the line that differs, and a test that needs no game data.

## What this plan keeps

These are the boundaries every phase below stays inside.

- Video and keyboard stay on **SDL2**. OpenAL stays the audio backend. Issue **#19** (an SDL3 backend) is out of this plan. The macOS packager already bundles the SDL3 library that Homebrew's `sdl2-compat` loads at runtime; that is a packaging detail, not a port.
- Saved classes stay the same bytes. `HouseClass` and `BuildingClass` are part of the `SAVEGAME_VERSION` sum in each `saveload.cpp`. A new field, a removed field, or a reordering changes what an old save means. Reordering two fields of the same size does not change the version number, and the load succeeds with the values in the wrong members.
- `EventClass` stays per game. Tiberian Dawn's `Frame` is 27 bits and `RALLY` is 27 (`tiberiandawn/event.h`). Red Alert's `Frame` is 26 bits and `RALLY` is 33, because `FIXIT_VERSION_3` in `redalert/defines.h` inserts the draw events ahead of it (`redalert/event.h`). `EventLength` and `EventNames` stay next to that enum (`tiberiandawn/event.cpp`, `redalert/event.cpp`). LAN games keep working only if every player runs a build with the same packet.
- Remastered DLLs stay **32-bit** and loadable by the Remastered Collection. `MEGAMAPS` stays off in those DLLs (issue **#1**). Standalone double-click selection and the production queue stay inside `#ifndef REMASTER_BUILD`.
- `common/` is compiled without `REMASTER_BUILD`. A standalone-only helper is a header included from the game file inside that guard, which is what `common/productionqueue.h` and `common/selectscan.h` already do.

## Findings

### Language

The project asks every compiler for C++11:

```89:90:CMakeLists.txt
set(CMAKE_CXX_STANDARD 11)
set(CMAKE_CXX_STANDARD_REQUIRED ON)
```

`common` repeats that with `target_compile_features(common PUBLIC cxx_std_11)` in `common/CMakeLists.txt`. `cmake/Compilers.cmake` turns extensions off, so the compiler is in standard mode, not "GNU mode" or "MSVC mode" with extra keywords.

What the CI compilers can actually compile, as of this review:

| Compiler | Where it runs | C++17 | C++20 |
| --- | --- | --- | --- |
| GCC 11, the default on `ubuntu-22.04` | `.github/workflows/linux.yml` | Complete | The language is mostly there. Some library pieces were finished in GCC 12. |
| Apple Clang on `macos-15` | `.github/workflows/macos.yml` | Complete | Complete for the features this code would use |
| Visual Studio 2022, same compiler for x86 and x64 | `.github/workflows/windows.yml` on `windows-2022` | Complete | Complete for the features this code would use |

**C++17 is the realistic target.** It is the newest standard all three have shipped complete for years. The features that help this code are ordinary ones: `std::optional` (a value that might be absent), `std::string_view` (a look at existing characters, no copy), `if constexpr`, and structured bindings. `std::make_unique` is C++14 and comes along with the bump.

**C++20 can wait.** Ranges, concepts, and modules are a larger style change, and GCC 11's C++20 library is not finished. Nothing in the tree needs them. `std::span` is the one C++20 type worth revisiting for buffer walks, after the Linux image moves to a newer GCC. **C++23 is not a target**; support is still uneven and this code does not need it.

One mechanical break blocks the bump. C++17 removed the old `register` keyword. It has been ignored by compilers for decades, and leaving it in a parameter or a local is a compile error under `/std:c++17` and `-std=c++17`. The real uses are:

- `tiberiandawn/coord.cpp`, `tiberiandawn/display.cpp`, `tiberiandawn/display.h`, `tiberiandawn/function.h`, `tiberiandawn/map.cpp` (`register int x, y`), `tiberiandawn/startup.cpp`
- `redalert/coord.cpp`, `redalert/display.cpp`, `redalert/display.h`, `redalert/function.h`

Comments that merely say "register" (`monoc.h` port numbers, mixfile log lines, `common/palette.cpp`) are fine. A scan of the tree found no `auto_ptr`, no `throw()` exception specifications, no `std::random_shuffle`, and no `std::unary_function`, which are the other C++17 removals that usually bite an old code base.

What is already in decent shape, and should stay the local style when a file is edited:

- `nullptr`, `override`, and `static_assert` in the newer code (`common/paths.*`, `common/productionqueue.h`, the skirmish settings headers).
- `MIN` / `MAX` / `ABS` as templates in `common/wwstd.h`.
- Bounded formatting (`snprintf`) on the lines already being edited. CI compiles with `-Werror=write-strings` on Linux and macOS and `/Zc:strictStrings` on Windows, so a string literal assigned to `char*` already fails CI.

What to leave in the Westwood style, because replacing it changes bytes or ownership the heaps depend on:

- `VectorClass` and `DynamicVectorClass` in `common/vector.h` (about a thousand lines). They are the lists the simulation walks. A `std::vector` stores objects differently and moves them when it grows. Anything that holds a pointer into the old vector breaks.
- The fixed heaps (`tiberiandawn/heap.h`, `redalert/heap.h`). A save writes the live objects out of those pools.
- The global `operator new` in `common/newdel.cpp`, which routes allocations through `Alloc()`. The heaps, the MIX loader, and the sound buffers assume that.
- `char` buffers and bitfields inside packed packets (`common/bitfields.h` marks GCC and Clang with `ms_struct` so their bitfields match MSVC). `std::string` inside `HouseClass` would save a pointer, not the text, and would change `sizeof(HouseClass)`.

A file-by-file pass that rewrites `NULL` to `nullptr` across the engines is churn. Do it in a file the day that file is already open for a bug.

- `WOLAPI_INTEGRATION` is never added by CMake. `redalert/rawolapi.cpp` compiles as an empty file, and the rest of Red Alert is full of `#ifdef WOLAPI_INTEGRATION` (`session.h`, `queue.cpp`, `house.h`, `stats.cpp`, `init.cpp`). The binary you ship is already the build without Westwood Online. Deleting the ifdefs is a large diff in files whose layout matters, for no player-visible change. Leave them until a change is already editing one of those functions.

`option(WIN9X)`, `option(DSOUND)`, and `option(DDRAW)` are declared twice when the target is Windows (`CMakeLists.txt` around the first option block and again inside `if(WIN32)`). CMake keeps the first declaration. One declaration each is enough.

### Build system and Ninja

CMake writes the build files. Ninja reads them and runs the compiler. The presets you actually use already ask for **Ninja Multi-Config**:

```9:13:CMakePresets.json
        {
            "name": "release",
            "displayName": "komkommer Release build",
            "generator": "Ninja Multi-Config",
            "binaryDir": "${sourceDir}/build/${presetName}",
```

`remaster`, `internal`, `testing`, and `nonet` inherit that generator. All three workflows run `cmake --workflow --preset release` or `remaster`, so CI is Ninja too. Linux installs `ninja-build`. Windows downloads Ninja **1.10.1** (2020) twice, once per job, then calls the same presets. macOS never installs Ninja and is trusting the `macos-15` image to have it.

"Multi-Config" means one configure, then you pick Debug or RelWithDebInfo at build time (`cmake --build --preset release --config Debug`). That is why the binaries land in `build/release/RelWithDebInfo/` and `build/release/Debug/`, which is what `README.md`, the tag workflows, and `scripts/package-macos.sh` expect. A plain `Ninja` generator (without "Multi-Config") picks the configuration once, when you configure, and drops the extra directory. Switching to it would move every output path. Keep Multi-Config. "Ninja everywhere" is already true for the presets that matter.

What is not Ninja:

```66:88:CMakePresets.json
        {
            "name": "msvc2019-i686-remaster",
            "inherits": "remaster",
            "binaryDir": "${sourceDir}/build_remaster",
            "displayName": "MSVC 2019 32bit Remaster build",
            "generator": "Visual Studio 16 2019",
            "architecture": "Win32"
        },
        {
            "name": "msvc2019-i686-vanilla",
            ...
            "generator": "Visual Studio 16 2019",
            "architecture": "Win32"
        },
        {
            "name": "msvc2019-x86-64-vanilla",
            "inherits": "release",
            "binaryDir": "${sourceDir}/build_msvc64",
            "displayName": "MSVC 2019 64bit komkommer build",
            "architecture": "x64"
        }
```

The two `i686` presets force **Visual Studio 16 2019**. The `x86-64` one inherits Ninja and only sets `architecture`. None of them have a build preset or a workflow preset. CI does not call them. `README.md` and `deploy.ps1` call `release` and `remaster`.

The `architecture` field is a Visual Studio generator feature. Ninja ignores it. You cannot rename those presets to Ninja and keep `"architecture": "Win32"` as the thing that produces a 32-bit DLL. With Ninja, bitness comes from which compiler is on `PATH`:

- **x86 Native Tools** prompt, then `cmake --preset remaster`. That is the 32-bit DLL. CI does the same thing with `ilammy/msvc-dev-cmd` and `arch: x86` before the workflow.
- **x64 Native Tools** prompt, then `cmake --preset release`. That is the standalone executables. CI uses `arch: x64`.

Ninja itself is a separate download. Visual Studio ships `ninja.exe` under its CMake extension directory, and the Native Tools prompt does not put it on `PATH`. Locally, install Ninja (`winget install Ninja-build.Ninja` is enough) and stay in the matching prompt. On the runner, stop fetching 1.10.1 twice; one install of a current Ninja, shared by both jobs, is the whole Windows change.

The Remastered preset does **not** check that the compiler is 32-bit. Configuring `remaster` from an x64 prompt produces 64-bit DLLs the Collection will not load. `deploy.ps1` checks the PE machine type afterwards. A configure-time check is earlier and harder to miss: if `BUILD_REMASTERTD` or `BUILD_REMASTERRA` is on and `CMAKE_SIZEOF_VOID_P` is not 4, `message(FATAL_ERROR ...)` with a sentence that says to open the x86 Native Tools prompt. Separate build trees per architecture stay mandatory (`README.md` already says this).

Other build nits, in the same small pull request as the presets:

- `windows.yml` creates `build/release/RelWithDebInfo` before configure so it can drop `SDL2.dll` there. That is a workaround for the runtime DLL, not a generator bug. Keep the copy, drop the duplicate Ninja download.
- macOS CI installs SDL2 and OpenAL from MacPorts, while `README.md` installs them from Homebrew. The tag job needs MacPorts because that is what the signed bundle is built against. A pull-request compile can follow the README and use Homebrew, and skip signing. Two dependency stories is a real cost; unifying them is a packaging change and can wait until the PR compile exists.
- `CMAKE_BUILD_TYPE` is forced to `RelWithDebInfo` near the top of `CMakeLists.txt` even for a multi-config generator, where that variable does nothing. Guarding it with "only when this is a single-config generator" removes a confusing cache entry. Behavior stays the same.
- `/MP` in `cmake/Compilers.cmake` is the MSVC multi-file compile flag. It still applies when Ninja invokes `cl`. Leave it.

### Testing

Seventeen CTest executables live in `tests/CMakeLists.txt`. They cover fixed-point and facing math, rectangles, fading tables, LCW, XOR delta, the random sequence, software drawing, screen shake, the shared selection scan, and the header-only skirmish settings. They link `common` or `commonv`. They do not link either game, and they do not read MIX files. The `testing` preset turns `BUILD_TESTS` on and turns **both games off**.

`cmake --workflow --preset testing` configures, builds, and runs CTest (`CMakePresets.json` workflow `testing`). Nothing in `.github/workflows/` calls it. `linux.yml`, `macos.yml`, and `windows.yml` all trigger only on:

```yaml
on:
  push:
    tags:
      - 'v*'
```

A pull request can merge with a compile break or a broken `tests/selectscan.cpp` and nobody finds out until a tag. The tag jobs also upload GitHub releases (`softprops/action-gh-release`, `contents: write`). A pull-request workflow must be a **different file**, so a CI run cannot publish a release.

One test bug to fix when that workflow lands. Most test targets compile with `$<$<CONFIG:DEBUG>:_DEBUG>`. The configuration name Ninja Multi-Config uses is `Debug`, and the rest of the tree spells it that way (`common/CMakeLists.txt`). The test form never matches, so a Debug test build does not define `_DEBUG`.

`TARGET_SYSTEM_EMULATOR` and `STATIC_LIBS` are expanded in `tests/CMakeLists.txt` and set nowhere. They are empty, so the test command is just the executable. Harmless. Delete them when that file is next edited, so the next reader does not go looking for a cross-emulator.

#### Where a test buys the most

Game logic is full of globals (`Map`, `PlayerPtr`, `Scen`, `Frame`, the object heaps, `OutList` / `DoList`). A test that needs a running map needs classic game data, which cannot be committed. The tests worth writing are the ones that fail in the compiler, or that run on plain numbers.

| Area | What to test | Needs game data? | Why it pays |
| --- | --- | --- | --- |
| Existing CTest | Run the 17 tests in CI | No | Stops the utilities and `selectscan` from rotting. Linux already has SDL2 and OpenAL installed for the game build, and the drawing tests link `commonv`, so they need those libraries at runtime. On Windows the SDL2 DLL has to sit beside the test exe, which the vanilla job already copies for the game. |
| INI | `INIClass` in `common/ini.cpp`: sections, ints, bools, missing keys, round-trip through a memory buffer | No | Skirmish settings and `conquer.ini` / `redalert.ini` sit on this parser. The skirmish tests already build an `INIClass` in memory. More cases are the same shape. `CCINIClass` typed getters (`Get_UnitType` and friends) need the game tables; skip those. |
| Save layout | `static_assert` on `offsetof` of sentinel fields, plus `sizeof` recorded **per compiler** | No, it is a compile of the game | `SAVEGAME_VERSION` is a sum of sizes. Swapping two `int` fields keeps the sum and breaks the save. TD's sum is `tiberiandawn/saveload.cpp` (`HouseClass`, `BuildingClass`, `CellClass`, …). RA's sum is `redalert/saveload.cpp` (adds `VesselClass`, `TriggerClass`, `ScenarioClass`, `ChronalVortexClass`). |

`HouseClass` layout asserts exist today and only on Linux x86_64 GCC, and only around the production queue (`tiberiandawn/house.h`, `redalert/house.h`). Players save and play LAN on Windows. MSVC x64 (standalone) and MSVC x86 (Remastered) pad structs differently, and the Remastered `HouseClass` is a different type because the queue fields are inside `#ifndef REMASTER_BUILD`. Record each of those sizes in its own `#if`. An assert with the Linux number inside the Windows DLL build would be a wrong failure. `BuildingClass` has no offset asserts at all; two sentinels (the field before `Rally` and the field after it, in each game) would cover the rally work.

The `testing` preset does not compile `house.cpp`. A CI job that only runs CTest will stay green while the game fails to build. The pull-request workflow has to run **both** the `release` preset (both executables) and the `testing` preset, and on Windows also the `remaster` preset under the x86 tool prompt.

## Phased plan

Each phase is one pull request, mergeable on its own. Later phases assume the earlier safety net is on `main`. Verification means "this is how you know the pull request did what it claims", and it is in addition to the new CI once phase 1 has landed.

### Phase 1 — CI on every push and pull request

**Scope.** A new `.github/workflows/ci.yml`. Triggers: `pull_request`, and `push` to `main`. No `contents: write`, no release upload.

- Linux (`ubuntu-22.04`): install the same packages `linux.yml` already installs. Run `cmake --workflow --preset release` and `cmake --workflow --preset testing`.
- Windows x64: the existing `ilammy/msvc-dev-cmd` `arch: x64` step, SDL2 and OpenAL as in `windows.yml`, `cmake --workflow --preset release`.
- Windows x86: `arch: x86`, `cmake --workflow --preset remaster`. Compile only. Do not zip or copy into a mods directory.
- macOS can follow in a second commit of the same PR if the first three are green: `brew install cmake ninja sdl2 openal-soft`, `cmake --workflow --preset release`, no signing, no MacPorts. If that job is slow, land the first three and add macOS as phase 1b.

Leave `linux.yml`, `macos.yml`, and `windows.yml` on `v*` tags. They remain the publishers.

**Risk.** Low. Workflow files only. A miswritten `on:` could start uploading releases from a pull request; the new file must not call `action-gh-release`.

**Verify.** Open a draft pull request that changes a comment. All three jobs pass. Push a commit that does not compile and confirm the Linux job fails. Confirm a tag is still the only thing that creates a release.

### Phase 2 — Small build corrections

**Scope.**

- In `tests/CMakeLists.txt`, `CONFIG:DEBUG` becomes `CONFIG:Debug`.
- In the root `CMakeLists.txt`, refuse a Remastered build whose pointer size is not 4, with a message that names the x86 Native Tools prompt.
